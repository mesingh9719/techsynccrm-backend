# Compliance and Google verification release checklist

Checked 25 October 2026. This is an implementation/release plan, not a finding of legal compliance or an approval from Google. Scope classifications/evidence gaps and estimates are in [02](02-google-requirements.md). No Cloud settings, public legal page or application configuration was changed in this task.

## Scope profiles and release artifacts

| Release profile | Requested access | Verification work before public launch |
|---|---|---|
| Foundation / identity | `openid email profile`; current Gmail adapter retains its existing separate grant | Confirm brand/domain/client setup; no new data-access claim merely because the facade exists. |
| Calendar dedicated scheduling | `calendar.app.created`; optional `calendar.freebusy` only at availability first use | Record exact Cloud Data Access classifications. Conservatively prepare sensitive review until confirmed. Scope-to-screen justification, event lifecycle video, reminder/privacy behavior and test-account proof. No R assessment claim merely because Calendar is sensitive. |
| Existing owned-calendar mode | `calendar.events.owned`; optional `calendar.calendarlist.readonly` | Separate incremental disclosure and classification/review update before public enablement. Explain why an app-created calendar is insufficient for this option. Do not request broad `calendar` as a shortcut. |
| Drive links/save and Sheets export/live intake | `drive.file` | NS classification is documented; comply with branding/policy/Production configuration, narrowly scoped token behavior and selected-file-only access. No sensitive/R verification introduced by this scope alone. |
| Broad Drive or legacy Gmail read/sync | R scopes if selected | Separate restricted-review/annual-assessment track for server-accessible data. Broad Drive is not recommended; Gmail read keeps its existing separate approval program. |

[Google scope/review guidance](https://developers.google.com/identity/protocols/oauth2/production-readiness/sensitive-scope-verification) requires least privilege and the project's Data Access declarations. For restricted server data, [Google's restricted guide](https://developers.google.com/identity/protocols/oauth2/production-readiness/restricted-scope-verification) describes annual approved assessment. Separate **projects**, not just client IDs, are the proposed Gmail/Workspace revocation boundary; do not split projects to evade review of the same app behavior.

## Cloud operator sequence (execute only after approval)

1. Inventory existing production/staging projects, OAuth client IDs, grant profiles, publishing state, verified scopes and who owns the projects. Confirm whether login/Gmail currently share a project. Retain existing callback URIs and live Gmail users. Establish staging vs production separation and a real support/security owner.
2. Verify `techsynchronic.com` ownership through the authorized Google project owner's Search Console account; list the required authorized domains, including the CRM subdomain as appropriate. Confirm the legal entity, app name/logo and support/developer emails use domains the business controls. Existing `techsynccrm.com` legal contacts must be verified or corrected deliberately.
3. Publish a working product homepage, Privacy Policy and Terms on the authorized domain. Suggested final URLs are `https://techsynchronic.com/privacy` and `/terms`; verify the actual canonical paths rather than assume these are deployed. They must be public, readable without CRM login, linked from product/consent and consistent across branding. Public fetches in this task were unavailable, so deployment/crawlability remains an operator check.
4. Enable **Google Calendar API**, **Google Drive API**, **Google Sheets API** and **Google Picker API** for the selected profile/projects as needed. Calendar-based Meet creation does not require enabling recordings/transcripts or broad Meet scopes. Existing Gmail API/Pub/Sub/KMS configuration remains a separate concern; enable Cloud KMS only if using the existing approved KMS envelope mode.
5. Configure External audience for a multi-customer SaaS, unless an actual single-domain internal deployment applies. Add controlled authorized test users for the pilot. “Internal” does not mean all of TechSync's unrelated customer domains.
6. Create a web OAuth client with exact production callback `https://crm.techsynchronic.com/api/google/oauth/callback` for the proposed Workspace flow and authorized JS origin `https://crm.techsynchronic.com`. Add approved staging/local URIs separately. Never derive a callback from an untrusted Host header. Do not replace Gmail or sign-in callbacks with the new route.
7. In Data Access add only each profile's actual scope set. Manually enter narrow Calendar scopes if absent from the searchable list; record the displayed classifications. Preserve denial/partial-grant behavior. No service feature is enabled solely because a historical scope happens to be returned.
8. Configure Picker API key restrictions, project number/App ID and same-project client matching. Current Google sample requires the appropriate app referrers plus `https://docs.google.com/*`, with API restrictions for Picker/Drive. Keep OAuth secrets/wrapping keys only on the server; public Picker config is not a secret. [Picker setup](https://developers.google.com/workspace/drive/picker/guides/web-picker-sample).
9. Configure and test the publicly trusted HTTPS Calendar push route. Calendar uses channel header/token validation, not Gmail Pub/Sub OIDC. Document firewall/reverse-proxy/header/log redaction and test an expired/unknown channel without exposing resource data. Keep polling fallback.
10. Record **effective** quotas, cohort/date, billing account requirement and current published rates/thresholds in a release sheet. No paid quota increase, assessor contract, new Redis or other paid infrastructure is authorized by this plan.
11. Test real consent with a controlled Google account and synthetic records; show selected-file access works without broad Drive. Capture actual granted scopes and behavior safely; never record real tokens in screenshots/videos/logs.
12. Submit branding and any sensitive/restricted scope review required; respond through project developer/support contacts and track the review status. Only enable public tenants after the applicable profile passes its gate.

Official [verification requirements](https://support.google.com/cloud/answer/13464321) describe homepage/policy/domain and video requirements. [Workspace app access controls](https://knowledge.workspace.google.com/admin/apps/control-which-apps-access-google-workspace-data) still apply after verification: provide the client ID and least-privilege scope explanation to a customer's admin; do not recommend disabling their security controls or blanket trust when specific access suffices.

## Privacy Policy additions: proposed publication copy

These are draft product-specific paragraphs for legal/business review and publication **when the described behavior exists**. Do not publish future functionality as present fact. Add a new dated policy version and keep consent versions tied to the features enabled.

**Google connection and control.** “You choose which Google features to connect. We use your selected Google account identity to show the account connected to this workspace. We request additional permissions when you enable a feature that needs them. Signing in with Google does not by itself enable access to your Google files or calendar.”

**Calendar.** “When you enable Calendar scheduling, TechSync creates or updates events linked to appointments or follow-ups you choose to schedule. We process the event identifiers, times, timezone, location, invitation details and optional meeting link needed for that service. In two-way mode, changes to linked events can update the corresponding CRM item. We do not import unrelated personal calendar events into your CRM. Optional availability checks use busy/free periods to help suggest a time. Invitations are sent only when you choose to invite guests.”

**Sheets.** “When you export to Google Sheets, selected CRM information is copied to the spreadsheet you choose or create. If you enable a continuous export or an incoming lead source, we read or update the configured tab and mapped fields on the schedule shown in the app. We retain identifiers and processing state to handle retries and report row errors. Spreadsheet owners and people they authorize may be able to access those external copies. Removing data or access in TechSync does not guarantee deletion of copies or revisions held in Google.”

**Drive.** “Attaching from Google Drive normally stores a reference and limited file metadata in TechSync, while the file contents remain in Google Drive. Linking a file does not change its Google sharing permissions. A CRM teammate may see the link yet still need permission from the file owner to open it. Save to Drive creates an external copy only when you request that action; your original TechSync file remains unless you separately delete it.”

**Security, retention and disconnect.** “We encrypt stored Google refresh credentials and restrict access to the services you enable. Turning a feature off stops its future use in the current workspace. Detaching a workspace connection removes its operational credentials and pauses dependent work. Removing Google's app access can affect other services or workspaces using the same Google project grant; we explain that before requesting it. Local operational logs are retained for 30 days and failed import snapshots for 7 days unless a shorter published tenant setting applies. Minimal audit identifiers are retained for up to 180 days under our audit policy. An encrypted revocation request may remain for up to 30 days solely to finish removing access, and is erased when completed or expired. External Google files and event invitations are not automatically deleted on disconnect.”

**Limited Use.** “We use Google API information only to deliver the Google features described here and requested in the app. We do not sell this information, use it for advertising or use it to train general-purpose AI models. Any transfer or human access is limited to what is necessary and permitted for the disclosed service, user-authorized support, security, legal obligations or other uses allowed by Google's policies. Our handling of Google API information follows the Google API Services User Data Policy and its Limited Use requirements.” Link to [Google's policy](https://developers.google.com/terms/api-services-user-data-policy).

**Deletion and support.** “You can turn features off, detach connections and request deletion through workspace settings or our published privacy contact. We remove local integration data according to the retention periods above; Google-hosted resources remain subject to their owners' permissions and Google's controls. Administrators can disable a member's connection within the workspace but cannot take over that member's private Google credentials.” Replace the privacy contact with the business's confirmed monitored address before publication.

Also reconcile the existing Gmail section: send-only connections do not read mailbox content; only separately enabled and consented mailbox-history grants can do so. Keep Gmail history retention/deletion disclosure distinct from new Calendar/Drive/Sheets logs. Do not silently reduce a previously promised deletion right or apply a new retention term retroactively.

## Terms additions and in-app notices

Draft Terms paragraph: “Connected Google services are optional and remain subject to Google's terms and the permissions granted by the Google account or organization administrator. You are responsible for authorizing the CRM information you export and for choosing appropriate recipients and file access. Changes to Google availability, quotas, ownership or permissions can delay or stop synchronization. Disconnecting a CRM integration does not automatically remove externally shared files, invitations or copies. TechSync records pending and failed operations and provides recovery controls, but does not guarantee uninterrupted synchronization or prevention of every scheduling conflict.”

Do not use these Terms to waive applicable statutory rights. Obtain appropriate review for clinics/minors/health information before promising relevant workflows; no medical-data processing or regulatory certification claim is created by adding a Drive link. In-product consent notices must match actual per-feature read/write/sharing, default to minimal event text and show export-copy consequences at confirmation.

## Demo video script and evidence pack

Use synthetic accounts/data and English consent UI. Provide an unlisted video link that shows the submitted app name/client and each requested scope in context; avoid cuts that hide a broad permission request. Never expose authorization codes or tokens.

1. Start on the public homepage; open Privacy/Terms without login, then sign into the CRM test workspace. Show current role and which features are off.
2. Connect Calendar; show the exact Google consent screen/app/client identity and optional availability request separately. Create one event, edit its time, explicitly invite a test guest/optional Meet if in submitted scope, and cancel it. Show the corresponding CRM item and minimal timeline content.
3. For two-way review, change/cancel the linked event in Google, show the CRM update and confirm that an unrelated personal event is not imported. Demonstrate a conflict/reconnect state if practical.
4. Connect Drive with `drive.file`; Picker-select one file, attach its link, show the no-sharing notice, open it in Google, then show a teammate access-denied case. Save one synthetic local file into a selected folder without deleting its original.
5. Export a filtered list to a new/selected spreadsheet/tab; show selected columns and external-copy notice. If continuous sync is in the submitted feature set, demonstrate direction, stable source key, mapping/preview, failed row, pause and recovery without duplicates.
6. Show admin service disable and member status without exposing private content; distinguish local disable/detach from project-wide revoke and demonstrate the applicable removal/deletion controls.

Evidence pack: scope-to-feature matrix and narrower-alternative justification; verified-domain and public-policy screenshots; consent/version records; client/project/profile inventory; data-flow/retention diagram; test credentials for reviewers via the approved secure process; redacted sync/security logs; QA results; incident/deletion/support contacts; and assessment documents only if R access requires them. Every declared scope must be used in the demonstrated build; remove speculative scopes.

## Launch and cost gates

Development with mocks can begin after owner approval. Controlled Testing/test-user operation can precede scope verification once configured, but is not an unrestricted customer release. Calendar U classifications need Console evidence and any required sensitive review. `drive.file` features may use the NS route after branding/policy/configuration validation; they must not inherit a restricted Gmail request. Existing mailbox-read verification is not automatically satisfied by verification of a different profile.

Use the timing/budget assumptions in [02](02-google-requirements.md): allow preparation/review/rework time, obtain real assessor quotes for R, and monitor Google's 2026 quota/billing notices. Do not describe a provisional allowance as Google's fixed CASA price or buy an assessment before a restricted feature is approved.
