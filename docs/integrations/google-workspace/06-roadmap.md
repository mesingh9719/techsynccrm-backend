# Phased delivery and launch gates

Proposal dated 25 October 2026. **Phase 0 code is now implemented and locally verified; external setup and live-account acceptance remain pending.** See [implementation](12-phase-0-implementation.md), [QA](13-phase-0-qa.md) and [Console setup](11-google-cloud-console-setup.md). Later phases still require their bounded approval. Original estimates below assume one experienced full-stack engineer familiar with this repo, part-time product/security input and separate QA. Ranges exclude Google waiting time and reserve 20–30% for independent QA/remediation; they are not commitments.

## Sequence

Foundation → Calendar one-way pilot → Drive and Sheets manual export → linked-only Calendar two-way → directional Sheets automations → advanced options. Calendar remains the highest-value scheduling work, but its public launch must not block non-sensitive `drive.file` features. Two-way Calendar is a separate release after one-way has proven its recovery and invitation behavior. Do not couple all three services into a single big-bang rollout.

## What starts or launches when

**After this plan is approved:** Phase 0 and mocked-provider Phase 1B can start immediately. No external customer credentials are needed for automated development. A controlled test-user pilot requires configured Cloud APIs/clients, privacy notices, authorized test users and explicit permission to operate their test calendars/files. Testing status has token/user restrictions; it is not general customer launch.

**Public non-sensitive path:** Phase 2 manual Drive/Sheets can launch without *sensitive/restricted scope verification* when only approved non-sensitive scopes are requested, branding/domain/policy and Production configuration are complete, no accidental Gmail/Calendar restricted grants enter this profile and test-account end-to-end checks pass. Brand verification/configuration may still be necessary. App access can still be blocked by a customer's Workspace admin.

**Calendar public path:** Capture the exact Console classifications for app-created and optional availability grants first. If S, wait for successful scope verification; if NS, use the non-sensitive gate; if R, revisit scope and assessment cost before launch. Treat Calendar as sensitive-gated until evidence resolves the uncertainty. A generic unverified-app bypass for up to 100 users is not the recommended commercial rollout.

**Restricted path:** No core feature needs broad Drive access. Existing Gmail mailbox read/sync has a separate verification/security-assessment release track. Do not import that compliance burden into Workspace inadvertently. No new restricted scope, paid assessor or Redis infrastructure is approved here.

Sources and checked facts are centralized in [02](02-google-requirements.md); exact verification artifacts in [07](07-compliance-and-verification.md).

## Release controls and measurable pilot targets

- Backend global flags + per-tenant service flags + per-user consent: all three must permit the action. Defaults off; operator can pause writes while retaining local CRM use, inspection, privacy cleanup and revocation.
- Start with 2–3 consenting internal/test workspaces and synthetic/nonclinical records. Limit selected syncs initially to 1 destination/source per workspace, 5,000 rows for live pilot and the existing 50k hard import ceiling. These are proposed operational pilot limits, not current commercial entitlements.
- Initial targets (estimates to validate): queued single-event writes p95 <60 seconds when Google/worker is healthy; webhook-to-reconciliation p95 <2 minutes; polling recovery within 15 minutes; no duplicate provider creates in crash/retry tests; all provider writes attributable to an authorized actor/operation. Display actual timestamps and delays rather than promising these SLOs publicly.
- Monitor sync lag, quota units/requests by project/user, token refresh/reconnect rates, watch renew failures, conflicts, ambiguous outcomes, failed-row counts and queue age. Do not attach customer cells or clinical text to telemetry.
- Gradually enable tenants only after logs and support playbooks are understood. Capture effective Cloud quotas/billing model; cap spend and defer paid quota increases to owner approval.

## Deployment and rollback

Reconfirm the actual host/process manager. Run migrations on isolated synthetic data first; then use the existing direct migration connection with an approved release. Keep API producer and `npm run worker` running separately with heartbeat/health checks and graceful shutdown. No new Redis service. Route `/api/webhooks/google/calendar` to the API over public HTTPS without login redirects, preserving X-Goog headers, rate limits and safe logging. Validate proxy trust, certificate renewal and service restart behavior.

Ship compatible additive tables, flags off, then API/worker, then frontend. Do not enable a feature until its worker handlers and recovery scans exist. Rollback: disable new writes/tenant flags, pause new operations, retain due-state records and privacy cleanup, revert compatible app release. Cancel uncertain operations only after reconciliation. Never bulk-delete Google events/files or drop populated mapping tables as an automatic rollback. Document any residual external invitations/copies and give operators a reviewed cleanup list.

## Decision checkpoints

Before Phase 0: approve shared facade/project boundary, local-vs-project revoke policy and no-Redis default. Before 1B: approve task scheduling semantics, calendar mode, guest/Meet and reminder defaults. Before 2: approve link/copy/sharing and export-off policy; test narrow Picker tokens. Before 3: approve stable source keys, manager authority, direction ownership, polling/retention and plan gates. Before 4: select specific features and reassess scopes, workload and legal requirements.
